# Password Security - Argon2id with Pepper

## Overview

Social Market uses **Argon2id** with **pepper** for password hashing, providing state-of-the-art security against modern attacks.

## Implementation

### Algorithm: Argon2id

Argon2id is the winner of the Password Hashing Competition (2015) and is recommended by:
- OWASP (Open Web Application Security Project)
- NIST (National Institute of Standards and Technology)
- Security experts worldwide

**Why Argon2id?**
- **Memory-hard**: Resistant to GPU/ASIC/FPGA attacks
- **Time-cost**: Configurable iteration count
- **Parallelism**: Multi-threaded for legitimate use, expensive for attackers
- **Hybrid**: Combines Argon2i (side-channel resistant) and Argon2d (GPU resistant)

### Hash Formula

```
hash = Argon2id(password + pepper, salt)
```

**Components:**
1. **Password**: User's password
2. **Pepper**: Secret server-side value (32+ bytes)
3. **Salt**: Random per-password value (16 bytes, auto-generated)

### Parameters

Our configuration follows OWASP recommendations for web applications:

```python
PasswordHasher(
    time_cost=3,           # 3 iterations
    memory_cost=65536,     # 64 MB = 65536 KB
    parallelism=4,         # 4 parallel threads
    hash_len=32,           # 256-bit hash
    salt_len=16,           # 128-bit salt
    type=Argon2id          # Hybrid algorithm
)
```

**Parameter Explanation:**
- **time_cost**: Number of iterations through memory
- **memory_cost**: Amount of RAM required (makes GPU attacks expensive)
- **parallelism**: Number of threads (balance security vs performance)
- **hash_len**: Output hash length in bytes
- **salt_len**: Random salt length in bytes

## Security Features

### 1. Pepper (Secret Salt)

**What is a Pepper?**
A pepper is a secret, server-side value added to passwords before hashing. Unlike salts:
- Stored in environment variable, NOT in database
- Same for all passwords
- Never exposed to users
- Adds an extra layer of security

**Benefits:**
- **Database Breach Protection**: Even if attacker steals database, they can't crack passwords without pepper
- **Rainbow Table Defense**: Pepper makes pre-computed attacks impossible
- **Key Rotation**: Can be rotated (with user migration)

**Pepper Storage:**
```bash
# .env file (never commit to git!)
PASSWORD_PEPPER=***REMOVED-PEPPER-SEE-docs/PASSWORD_SECURITY.md***
```

**Generation:**
```bash
python3 -c "import secrets; print(secrets.token_hex(32))"
```

### 2. Salt (Random Per-Password)

**What is a Salt?**
A unique random value generated for each password.

**Benefits:**
- Prevents rainbow table attacks
- Makes identical passwords hash differently
- Automatically generated by argon2-cffi
- Stored in hash string (safe to store in database)

**Example:**
```
User A: password123 + pepper + salt1 = hash1
User B: password123 + pepper + salt2 = hash2
(different hashes even with same password)
```

### 3. Memory Hardness

Argon2id requires 64 MB of RAM per hash computation.

**Why This Matters:**
- GPUs have limited memory per core
- Makes parallel cracking expensive
- Each password guess costs 64 MB RAM
- Cracking 1M passwords simultaneously = 64 TB RAM (infeasible)

### 4. Time Cost

3 iterations through memory = ~0.2-0.5 seconds per hash on typical servers.

**Trade-offs:**
- Legitimate users: 0.2s is imperceptible
- Attackers: 0.2s per guess = only 5 guesses/second
- With 8-character lowercase password: 26^8 combinations = 10^5 years to crack

## Hash Format

Argon2id produces hashes in PHC string format:

```
$argon2id$v=19$m=65536,t=3,p=4$saltbase64$hashbase64
```

**Breakdown:**
- `$argon2id$`: Algorithm identifier
- `v=19`: Version 1.3 (latest)
- `m=65536`: Memory cost (64 MB)
- `t=3`: Time cost (3 iterations)
- `p=4`: Parallelism (4 threads)
- `saltbase64`: Base64-encoded salt
- `hashbase64`: Base64-encoded hash

### Automatic Hash Upgrade

The system automatically upgrades legacy hashes:

```python
def check_password(self, password):
    # Check for legacy pbkdf2/scrypt hashes
    if self.password_hash.startswith('pbkdf2:'):
        is_valid = check_password_hash(self.password_hash, password)

        if is_valid:
            # Upgrade to Argon2id
            self.set_password(password)
            db.session.commit()

        return is_valid

    # Verify Argon2id hash
    return password_service.verify_password(password, self.password_hash)
```

## Best Practices

### 1. Pepper Management

**DO:**
- Generate pepper with cryptographically secure random function
- Store in environment variable (.env file)
- Use minimum 32 bytes (64 hex characters)
- Backup pepper securely offline
- Document pepper location in deployment guides
- Use different peppers for dev/staging/production

**DON'T:**
- Never commit pepper to git
- Never hardcode pepper in source code
- Never share pepper via insecure channels
- Never use same pepper across multiple applications
- Never store pepper in database

### 2. Pepper Rotation

To rotate pepper without disrupting users:

1. Add new pepper to config (`PASSWORD_PEPPER_NEW`)
2. Update hashing to use new pepper
3. Modify verification to try both peppers
4. Users' passwords auto-upgrade on next login
5. After 90 days, remove old pepper

Example:
```python
def verify_password(self, password):
    # Try new pepper first
    if password_service.verify_password(password, self.password_hash):
        return True

    # Fallback to old pepper
    old_service = PasswordService(old_pepper=True)
    if old_service.verify_password(password, self.password_hash):
        # Upgrade to new pepper
        self.set_password(password)
        db.session.commit()
        return True

    return False
```

Track password hashing performance:

```python
    logger.warning(f"Slow password hash: {elapsed:.2f}s")
```

### 5. Migration Strategy

When upgrading from old hashing:

1. **Don't force password resets** - users hate this
2. **Upgrade on login** - transparent to users
3. **Keep compatibility** - verify old hashes during transition
4. **Monitor progress** - track how many users upgraded
5. **Clean up** - remove old hashing code after 99% migrated

## Threat Model

### Attacks Defended Against

✅ **Rainbow Tables**: Pepper + salt makes pre-computation impossible
✅ **Dictionary Attacks**: High time cost limits guesses per second
✅ **Brute Force**: Memory cost makes parallel attacks expensive
✅ **GPU Cracking**: Memory requirements exceed GPU capacity
✅ **ASIC Cracking**: Custom hardware too expensive
✅ **Database Breach**: Pepper not in database, hashes useless
✅ **Side-Channel Attacks**: Constant-time operations
✅ **Timing Attacks**: Constant-time comparison

### Remaining Risks

⚠️ **Weak Passwords**: No hashing can fix "password123"
⚠️ **Phishing**: Users tricked into giving passwords
⚠️ **Keyloggers**: Malware on user's device
⚠️ **Server Compromise**: If pepper is exposed, hashes can be cracked
⚠️ **Social Engineering**: User gives password to attacker

**Mitigations:**
- Enforce strong password policies
- Require 2FA for sensitive accounts
- Rate limit login attempts
- Monitor for suspicious activity
- Educate users about phishing

## Performance Considerations

### Hash Time: ~0.2-0.5 seconds

**Impact:**
- Login: User waits 0.2s (imperceptible)
- Registration: User waits 0.2s (acceptable)

## FAQ

**Q: Can I use bcrypt instead?**
A: Bcrypt is acceptable but Argon2id is more secure. We recommend Argon2id.

**Q: What if pepper is compromised?**
A: Generate new pepper, rotate it, force password resets for high-value accounts.

**Q: How long should pepper be?**
A: Minimum 32 bytes (64 hex chars). Longer is fine but doesn't add much security.

**Q: Can I store pepper in database?**
A: No! Pepper must be stored outside database (environment variable).

**Q: What if I lose the pepper?**
A: All passwords become unverifiable. Users must reset. Backup pepper carefully.

**Q: How often should I rotate pepper?**
A: Annually, or after any security incident. With proper rotation strategy.

**Q: Is 64 MB memory cost too much?**
A: No, it's the recommended amount for web apps. Can reduce to 32 MB if needed.

**Q: Why not higher time cost?**
A: 3 iterations is the OWASP recommendation. Higher causes noticeable delays.
